# Admin API CI/CD and release runbook

PR approval does not activate the pipeline or authorize infrastructure changes. Frank merges pull requests. Database migrations remain separate approved changes.

## Automatic release after setup

The active workflow is `.github/workflows/ci.yml`. Critical image findings fail CI and deployment; high findings are reported as warnings with details in the job log. Scanner execution errors remain failures. Pull requests run client and API checks and build and scan an AMD64 image on GitHub-hosted runners. A master push or manual master dispatch runs those checks first. When `BP_AUTO_DEPLOY_ENABLED=true`, the deploy job rebuilds and scans the release image, pushes it to the private Amazon ECR repository `beerpassport-admin-api` in us-east-1 (account 149290600858) using the existing GitHub OIDC deployment role, captures the digest, and invokes version 2 of the fixed `BeerPassportDeployAdmin` Systems Manager document. The document accepts only a SHA-256 digest and invokes `/opt/beerpassport-admin/deploy-api.sh` with the fixed ECR repository. CI does not run migrations. Concurrent deployment jobs are serialized; a job checks that its commit is still master before publishing and before requesting deployment. CI reports SSM execution failures. The API release is therefore automatic after merge only once the setup below has been explicitly approved and completed.

Version 1 of the deploy document, which references the pre-migration Docker Hub repository, is retained unchanged: it is the rollback path to the currently running Docker Hub image until an ECR release has been verified and itself becomes the recorded rollback target.

Lightsail must be registered as a Systems Manager hybrid managed node. AWS lists no hybrid-node registration charge and $0.002 per Run Command invocation as of 2026-11-23; ten deployments cost about $0.02 in command charges. ECR storage is $0.10 per GB-month; the API image costs a few cents per month. GitHub Actions minutes and network bandwidth depend on plan and usage. Verify current pricing before setup. Install the reviewed deployment scripts at `/opt/beerpassport-admin/` as root-owned, not writable by the application or its runtime accounts. The existing root-only env file is `/etc/beerpassport/secrets/admin-api.env`. The deploy script preserves localhost port binding, attaches the internal database network, verifies HTTP liveness and a database read, and attempts rollback on failure. Rehearse startup, network and DB failures on disposable infrastructure before enabling.

## How the Lightsail host pulls from ECR

ECR login tokens expire after 12 hours and the host has no AWS CLI, so no stored Docker login can stay valid between deployments. Instead, every ECR deployment refreshes authentication immediately before pulling:

- `scripts/deploy-api.sh` detects an ECR image reference and runs `scripts/ecr-login.py` (Python 3 standard library only; it makes the signed ECR `GetAuthorizationToken` call directly, with no AWS CLI). The returned password is piped to `docker login --password-stdin` and never printed or logged.
- The login uses a temporary `DOCKER_CONFIG` directory that the deploy script deletes when it exits, so no registry credential persists on disk. Authentication and the pull both complete before the running container is touched; an authentication failure aborts the deployment with the service untouched.
- The pull identity is deliberately minimal (see `lightsail-ecr-pull-policy.example.json`: `GetAuthorizationToken` plus pull actions on the one repository only; `GetAuthorizationToken` does not support resource-level permissions, so its statement uses `"Resource": "*"` and the token is only useful with the repository-scoped pull actions). Primary path, as configured on the host: the SSM managed-node IAM role carries that policy, and the SSM Agent maintains its temporary credentials in `/root/.aws/credentials` (default profile, including the session-token field), which is exactly what the login helper reads when the deploy runs as root. There is no long-lived credential on the host. Fallback, only if that file proves unusable: create the dedicated IAM user `beerpassport-lightsail-ecr-pull` with the same policy and place its access key, root-only and mode 0600, in `/etc/beerpassport/secrets/aws-ecr-pull.env`; the login helper reads that file first when present.
- Docker Hub references never take this path, so rollback to the pre-migration image is unaffected by ECR authentication.
- Gate before enabling deployment: the mock-tested login flow is not evidence against real AWS. A real ECR login AND a real pull of a published image digest must be run successfully on the host (setup step 5) before `BP_AUTO_DEPLOY_ENABLED` is set.

## Required one-time setup (each production change requires Frank's approval)

Already in place (verified against the actual AWS setup; do not recreate any of these): the ECR repository `beerpassport-admin-api` in us-east-1; the GitHub OIDC deployment role, which already has push permission to that repository (`docs/ci-cd/github-ecr-push-policy.example.json` now documents that existing scope); the SSM hybrid managed node and its IAM role; and version 1 of the `BeerPassportDeployAdmin` document (the Docker Hub variant, retained for rollback). GitHub OIDC configuration is likewise unchanged (`aud=sts.amazonaws.com`, exact `repo:FrankPizz10/beer-passport-admin:ref:refs/heads/master` subject, `ssm:SendCommand` only for the document and the managed node).

1. Merge the ECR migration PR, including installing the updated `.github/workflows/ci.yml` from `docs/ci-cd/workflows/ci.yml`. Keep `BP_AUTO_DEPLOY_ENABLED` absent or false until every step below is verified. Do not assume a workflow environment automatically enforces an approval.
2. Set (or verify) the GitHub variable `BP_ECR_REGISTRY` to `149290600858.dkr.ecr.us-east-1.amazonaws.com`.
3. Add document version 2 from `docs/ci-cd/ssm-deploy-document.v2.json`: `aws ssm update-document --name BeerPassportDeployAdmin --content file://docs/ci-cd/ssm-deploy-document.v2.json --document-version '$LATEST'`. This creates version 2 alongside the existing version 1; the workflow pins version 2 explicitly. Neither version accepts arbitrary command text.
4. Confirm the managed-node IAM role carries the pull policy from `docs/ci-cd/lightsail-ecr-pull-policy.example.json` (attach it if it is not already there), and install the reviewed root-owned scripts on the host, including `ecr-login.py` (executable). Restrict script ownership and permissions.
5. Verify the pull path on the host for real, before any deployment is enabled: run `/opt/beerpassport-admin/ecr-login.py 149290600858.dkr.ecr.us-east-1.amazonaws.com` as root (it reads the default profile, including the session token, from `/root/.aws/credentials`) and then pull a published image by digest, for example `docker pull 149290600858.dkr.ecr.us-east-1.amazonaws.com/beerpassport-admin-api@sha256:<a published digest>`. Both must succeed; if the agent credentials file proves unusable, use the fallback IAM user from the pull-path section and repeat this verification.
6. Apply the separately reviewed image-workflow migration, viewer grant, and approver role only after a verified backup and explicit approval. Verify the role, securely set `DATABASE_URL_WRITE`, and confirm the first release has a rollback plan.
7. Cutover, explicitly approved: set `BP_AUTO_DEPLOY_ENABLED=true` and dispatch the workflow on master. Verify the published digest in ECR, the SSM result, HTTPS health, the authenticated queue and database access. The deploy script records the currently running Docker Hub image as the rollback target before switching, so the first ECR release can be rolled back with `scripts/rollback-api.sh` (or by invoking document version 1 with that digest). Only after the ECR release is verified: revoke the Docker Hub access token and delete the `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` GitHub secrets. Keep document version 1 and the host's local copy of the Docker Hub image.

## Netlify ordering

Netlify currently publishes master independently and can outrun the API. This pipeline does not control Netlify. Until a separate coordinated client release is implemented, maintain client compatibility with the currently deployed API or hold Netlify publishing and release the API first. Merge approval alone does not make an incompatible simultaneous client/API change safe. Compatibility probe for the image queue: an unauthenticated `GET /admin-api/v1/images/queue` returns 404 against an API that predates the image workflow and 401 against the current API; publish a client that needs the queue only after the probe returns 401.

## Recovery

The script records the prior image and retains the old container. On a failed switch it attempts restoration; confirm the old service is healthy. For a later rollback use the reviewed rollback script after Frank's approval; rollback works across registries, because the recorded target is a full image reference and Docker Hub references skip ECR authentication entirely. An ECR authentication failure happens before any switch and needs no rollback: fix the pull identity or credentials file and re-run. Stop auto deployment by setting `BP_AUTO_DEPLOY_ENABLED=false` and investigate. Keep database backups; an API rollback does not undo migrations. Scan results are a point-in-time view; rebuild on Node and base-image security updates.
