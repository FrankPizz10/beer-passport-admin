# Admin API CI/CD and release runbook

PR approval does not activate the pipeline or authorize infrastructure changes. Frank merges pull requests. Database migrations remain separate approved changes.

## Automatic release after setup

The active workflow is `.github/workflows/ci.yml`. Critical image findings fail CI and deployment; high findings are reported as warnings with details in the job log. Scanner execution errors remain failures. Pull requests run client and API checks and build and scan an AMD64 image on GitHub-hosted runners. A master push or manual master dispatch runs those checks first. When `BP_AUTO_DEPLOY_ENABLED=true`, the deploy job rebuilds and scans the release image, pushes it to the private Amazon ECR repository `beer-passport-admin-api` in us-east-1 (account 149290600858) using the existing GitHub OIDC deployment role, captures the digest, and invokes version 2 of the fixed `BeerPassportDeployAdmin` Systems Manager document. The document accepts only a SHA-256 digest and invokes `/opt/beerpassport-admin/deploy-api.sh` with the fixed ECR repository. CI does not run migrations. Concurrent deployment jobs are serialized; a job checks that its commit is still master before publishing and before requesting deployment. CI reports SSM execution failures. The API release is therefore automatic after merge only once the setup below has been explicitly approved and completed.

Version 1 of the deploy document, which references the pre-migration Docker Hub repository, is retained unchanged: it is the rollback path to the currently running Docker Hub image until an ECR release has been verified and itself becomes the recorded rollback target.

Lightsail must be registered as a Systems Manager hybrid managed node. AWS lists no hybrid-node registration charge and $0.002 per Run Command invocation as of 2026-11-23; ten deployments cost about $0.02 in command charges. ECR storage is $0.10 per GB-month; the API image costs a few cents per month. GitHub Actions minutes and network bandwidth depend on plan and usage. Verify current pricing before setup. Install the reviewed deployment scripts at `/opt/beerpassport-admin/` as root-owned, not writable by the application or its runtime accounts. The existing root-only env file is `/etc/beerpassport/secrets/admin-api.env`. The deploy script preserves localhost port binding, attaches the internal database network, verifies HTTP liveness and a database read, and attempts rollback on failure. Rehearse startup, network and DB failures on disposable infrastructure before enabling.

## How the Lightsail host pulls from ECR

ECR login tokens expire after 12 hours and the host has no AWS CLI, so no stored Docker login can stay valid between deployments. Instead, every ECR deployment refreshes authentication immediately before pulling:

- `scripts/deploy-api.sh` detects an ECR image reference and runs `scripts/ecr-login.py` (Python 3 standard library only; it makes the signed ECR `GetAuthorizationToken` call directly, with no AWS CLI). The returned password is piped to `docker login --password-stdin` and never printed or logged.
- The login uses a temporary `DOCKER_CONFIG` directory that the deploy script deletes when it exits, so no registry credential persists on disk. Authentication and the pull both complete before the running container is touched; an authentication failure aborts the deployment with the service untouched.
- The pull identity is deliberately minimal (see `lightsail-ecr-pull-policy.example.json`: `GetAuthorizationToken` plus pull actions on the one repository only). Primary setup: attach that policy to the host's existing SSM managed-node IAM role. Its credentials are temporary and are refreshed by the SSM Agent, which maintains them in the root shared credentials file the login helper reads, so there is no long-lived credential on the host at all. Fallback setup, if the agent credentials file proves unusable during setup verification: create the dedicated IAM user `beer-passport-lightsail-ecr-pull` with the same policy and place its access key, root-only and mode 0600, in `/etc/beerpassport/secrets/aws-ecr-pull.env`; the login helper reads that file first when present.
- Docker Hub references never take this path, so rollback to the pre-migration image is unaffected by ECR authentication.

## Required one-time setup (each production change requires Frank's approval)

1. Merge the ECR migration PR. Keep `BP_AUTO_DEPLOY_ENABLED` absent or false until all setup and the first ECR release are complete. Do not assume a workflow environment automatically enforces an approval.
2. Create the ECR repository and attach the push policy to the existing OIDC deployment role (Frank runs these from his Mac; the agent's AWS access is read-only):
   - `aws ecr create-repository --repository-name beer-passport-admin-api --image-tag-mutability IMMUTABLE --image-scanning-configuration scanOnPush=true --region us-east-1`
   - Create a policy from `docs/ci-cd/github-ecr-push-policy.example.json` and attach it to the deployment role used in `BP_DEPLOY_ROLE_ARN`. The role's SSM permissions and trust do not change.
   - Set the GitHub variable `BP_ECR_REGISTRY` to `149290600858.dkr.ecr.us-east-1.amazonaws.com`.
3. Install and register SSM Agent on Lightsail through a one-node hybrid activation and a dedicated minimal managed-node IAM role (unchanged from the original setup). Record the resulting `mi-...` ID in GitHub variable `BP_SSM_NODE_ID`; do not expose activation codes.
4. Create document version 2 from `docs/ci-cd/ssm-deploy-document.v2.json` and install the reviewed root-owned scripts on the host, including `ecr-login.py` (executable):
   - `aws ssm update-document --name BeerPassportDeployAdmin --content file://docs/ci-cd/ssm-deploy-document.v2.json --document-version '$LATEST'` (this creates version 2; the workflow pins version 2 explicitly, and version 1 stays intact for rollback)
   - Restrict script ownership and permissions; neither document version accepts arbitrary command text.
5. Set up the host pull identity. Primary: create a policy from `docs/ci-cd/lightsail-ecr-pull-policy.example.json` and attach it to the managed-node IAM role, then verify on the host that the SSM Agent credentials file exists and a manual run of `/opt/beerpassport-admin/ecr-login.py 149290600858.dkr.ecr.us-east-1.amazonaws.com` succeeds. Fallback (only if that verification fails): `aws iam create-user --user-name beerpassport-lightsail-ecr-pull`, attach the same policy, `aws iam create-access-key --user-name beerpassport-lightsail-ecr-pull`, and have Frank write the key pair into `/etc/beerpassport/secrets/aws-ecr-pull.env` on the host (root-only, 0600) through a secure path, never through chat, Git, or logs; re-run the same manual login verification.
6. GitHub OIDC stays as originally set up (`aud=sts.amazonaws.com`, exact `repo:FrankPizz10/beer-passport-admin:ref:refs/heads/master` subject, dedicated deploy role, `ssm:SendCommand` only for the `BeerPassportDeployAdmin` document and managed-node ARN). Protect master and workflow modifications.
7. Test the pinned document versions and IAM policies with a harmless disposable node; verify denial for other documents, nodes, malformed digests, and non-master OIDC subjects. Never test with production mutations without approval.
8. Apply the separately reviewed image-workflow migration, viewer grant, and approver role only after a verified backup and explicit approval. Verify the role, securely set `DATABASE_URL_WRITE`, and confirm the first release has a rollback plan.
9. Cutover, explicitly approved: set `BP_AUTO_DEPLOY_ENABLED=true` and dispatch the workflow on master. Verify the published digest in ECR, the SSM result, HTTPS health, the authenticated queue and database access. The deploy script records the currently running Docker Hub image as the rollback target before switching, so the first ECR release can be rolled back with `scripts/rollback-api.sh` (or by invoking document version 1 with that digest). Only after the ECR release is verified: revoke the Docker Hub access token and delete the `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` GitHub secrets. Keep document version 1 and the host's local copy of the Docker Hub image.

## Netlify ordering

Netlify currently publishes master independently and can outrun the API. This pipeline does not control Netlify. Until a separate coordinated client release is implemented, maintain client compatibility with the currently deployed API or hold Netlify publishing and release the API first. Merge approval alone does not make an incompatible simultaneous client/API change safe. Compatibility probe for the image queue: an unauthenticated `GET /admin-api/v1/images/queue` returns 404 against an API that predates the image workflow and 401 against the current API; publish a client that needs the queue only after the probe returns 401.

## Recovery

The script records the prior image and retains the old container. On a failed switch it attempts restoration; confirm the old service is healthy. For a later rollback use the reviewed rollback script after Frank's approval; rollback works across registries, because the recorded target is a full image reference and Docker Hub references skip ECR authentication entirely. An ECR authentication failure happens before any switch and needs no rollback: fix the pull identity or credentials file and re-run. Stop auto deployment by setting `BP_AUTO_DEPLOY_ENABLED=false` and investigate. Keep database backups; an API rollback does not undo migrations. Scan results are a point-in-time view; rebuild on Node and base-image security updates.
